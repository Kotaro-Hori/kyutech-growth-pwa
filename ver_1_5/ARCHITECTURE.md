# 将来の他チーム提供を考慮した設計方針（草案）

## 現状と目的

現状は1台の端末に保存する単一チームの試作です。将来の販売、運営主体、料金設定は未決定です。まずKyutech鹿児島向けで検証し、他チームに提供可能な構造へ段階的に移行します。

## 将来の推奨構成

- `organizations`: サービス運営組織。`organization_id` を永続的な識別子とする
- `teams`: 契約・利用チーム。`team_id`, `organization_id` を持つ
- `users`: ログイン主体。個人の認証ID
- `memberships`: `user_id`, `team_id`, `role` で所属と役割を定義。複数所属を許容
- `players`: `player_id`, `team_id`。名前はIDにしない。転籍・卒団履歴も別管理
- `guardians`: `user_id`, `player_id` による家庭ごとの参照範囲
- `staff_assignments`: スタッフ・選手・期間に紐づく担当
- `records`: 競技成績、トレーニング、InBody、パフォーマンス測定を分類。記録IDは不変
- `metric_definitions` と `training_definitions`: チーム単位で管理する追加・更新可能な項目
- `goals`, `messages`, `files`, `audit_logs`: 所属チーム・作成者・変更時刻と結びつける

全テーブルについてサーバー側で、ユーザーが対象の `team_id` に所属しているか、対象の `player_id` を閲覧できるかを検証します。フロント画面からボタンを消すだけではアクセス制御になりません。

## 注意点

1. **既存データを壊さない**: 端末保存のキー、選手ID、記録IDは変更せずに拡張
2. **権限管理**: ログインとサーバー側認可は別。管理者にも必要最小限のアクセス
3. **オフライン同期**: ローカル変更ID、同期状態、競合の解決方針、失敗時の再送・重複排除が必要
4. **測定指標**: 単位、良い方向（大/小）、測定方式、改訂履歴をデータとして保持
5. **個人情報保護**: 未成年者の身体情報、画像、家庭とのメッセージは本番環境では権限分離、監査、保存期間、バックアップ、削除手順が必須
6. **運営引き継ぎ**: ソースコード・ドメイン・クラウド・料金支払い・リリース手順の管理権限を事業主体が継続保有できるようにする
7. **公開方式**: GitHub Pagesは開発デモ向け。将来の商用SaaS配信には別の本番基盤を選ぶ

## この版では未対応

複数チームの作成、チーム切替、サーバー認証、テナント間隔離、クラウドDB、オフライン同期、エクスポートの暗号化、課金、契約、運営者管理。これらを搭載したと誤解しないこと。
